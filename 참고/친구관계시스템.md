친구관계 시스템에 대해 설명해볼께.



친구는 가족/찐친/친구 이렇게 되어있어.



A가 B에게 친구신청을 할 때에 B에 대해 가족/찐친/친구 중 선택을 하고 신청을 보낼 수 있어.

그럼 B는 A의 친구신청을 수락 또는 거절 할 수 있는데 수락할 때 가족/찐친/친구 중 선택을 할 수 있어.



예를들어 A는 B를 찐친 으로 선택하고 신청을 보냈는데 B는 A를 친구 로 선택하고 수락을 했어.



이럼 A에게 B는 찐친이고 B에게 A는 친구야.



A가 만약 일기를 작성할때 찐친만 볼 수 있게 설정을 했다면 B가 볼 수 있는거야.

그럼 B의 친구소식에 A의 해당 일기가 표시가 되는거지.



반대로 B가 만약 일기를 작성할 때 찐친만 볼 수 있게 설정되 있다면 A는 볼 수가 없어.

그럼 A의 친구소식에 B의 해당 일기가 표시되지 않는거지.



시스템을 이해했으면 DB설계를 할 수 있게 md파일로 만들어줘.

제시해주신 흥미로운 친구 관계 시스템을 완벽하게 이해했습니다. 핵심은 **"관계는 상호적(Mutual)이지만, 관계에 대한 정의(Type)는 비대칭적(Asymmetric)이다"**는 점입니다.

A와 B가 친구가 되려면 서로 동의해야 하지만, A가 B를 생각하는 마음(예: 찐친)과 B가 A를 생각하는 마음(예: 친구)은 다를 수 있다는 현실적인 관계를 잘 반영한 시스템이네요. 또한 이 관계 정의가 콘텐츠(일기)의 접근 권한과 직결된다는 점도 명확합니다.

이 요구사항을 만족하는 DB 스키마를 설계해 보았습니다. 관계형 데이터베이스(RDBMS, 예: MySQL, PostgreSQL) 기준으로 작성되었습니다.

친구 관계 시스템 DB 설계
1. 설계 핵심 전략
가장 중요한 부분은 A와 B가 친구가 되었을 때, 이 관계를 어떻게 저장하느냐입니다.

잘못된 접근: 하나의 행(Row)에 A와 B의 관계를 모두 넣는 것. (예: user1: A, user2: B, type1_view: 찐친, type2_view: 친구) -> 쿼리가 매우 복잡해지고 확장성이 떨어집니다.

올바른 접근 (채택): 관계를 방향성 있는 그래프의 간선(Edge)처럼 취급하여 두 개의 행(Row)으로 나누어 저장하는 것입니다.

행 1: 주체(A)가 대상(B)을 어떻게 생각하는가 (A -> B : 찐친)

행 2: 주체(B)가 대상(A)을 어떻게 생각하는가 (B -> A : 친구)

이렇게 설계하면 "A가 쓴 글을 B가 볼 수 있는가?"를 판단할 때, "A가 B를 어떻게 정의했는가"만 조회하면 되므로 로직이 매우 간결해집니다.

3. 테이블 상세 정의
3.1. users (사용자 테이블)
기본적인 사용자 정보를 저장합니다.

컬럼명	데이터 타입	PK/FK	설명
user_id	BIGINT	PK	사용자 고유 ID (Auto Increment)
nickname	VARCHAR(50)		닉네임
created_at	DATETIME		가입일
3.2. relationship_types (관계 타입 정의 테이블)
'가족', '찐친', '친구'라는 고정된 타입을 관리하는 테이블입니다. 별도 테이블로 분리하면 추후 타입이 추가되거나 변경될 때 유연하게 대처할 수 있습니다.

컬럼명	데이터 타입	PK/FK	설명
type_id	INT	PK	타입 고유 ID (예: 1, 2, 3)
type_name	VARCHAR(20)		타입 명칭 (예: '가족', '찐친', '친구')
priority	INT		(옵션) 타입 간 우선순위/계층. 숫자가 낮을수록 더 친밀함.
초기 데이터 예시:

(1, '가족', 10)

(2, '찐친', 20)

(3, '친구', 30)

3.3. friend_requests (친구 신청 대기 테이블)
친구가 되기 전, 신청 상태를 관리하는 테이블입니다. 수락 또는 거절 시 이 테이블의 상태가 변경되거나 데이터가 삭제됩니다.

컬럼명	데이터 타입	PK/FK	설명
request_id	BIGINT	PK	신청 고유 ID
sender_id	BIGINT	FK	신청을 보낸 사람 (A)
receiver_id	BIGINT	FK	신청을 받은 사람 (B)
sender_proposed_type_id	INT	FK	신청자가 선택한 상대방의 타입 (A가 생각하는 B)
status	VARCHAR(20)		상태 (PENDING, REJECTED 등. 수락되면 friendships로 이동)
created_at	DATETIME		신청 일시
3.4. friendships (친구 관계 핵심 테이블) 🌟
이 시스템의 핵심 테이블입니다. 성사된 친구 관계를 정의합니다. 반드시 (user_id, friend_id) 조합이 유니크해야 하며, 이 두 컬럼이 복합 기본키(Composite PK)가 됩니다.

컬럼명	데이터 타입	PK/FK	설명
user_id	BIGINT	PK, FK	관계를 정의하는 주체 (나)
friend_id	BIGINT	PK, FK	관계의 대상이 되는 친구 (너)
assigned_type_id	INT	FK	내가 이 친구를 무엇으로 설정했는지 (relationship_types 참조)
created_at	DATETIME		친구가 된 일시
동작 프로세스 예시 (중요)
A가 B에게 '찐친'으로 신청하고, B가 A를 '친구'로 수락하는 순간 트랜잭션으로 두 개의 행이 동시에 INSERT 됩니다.

INSERT INTO friendships (user_id, friend_id, assigned_type_id) VALUES (A, B, '찐친_ID');

(해석: A 입장에서 B는 찐친이다)

INSERT INTO friendships (user_id, friend_id, assigned_type_id) VALUES (B, A, '친구_ID');

(해석: B 입장에서 A는 친구다)

3.5. diaries (일기 예시 테이블)
관계 기반의 접근 제어를 테스트하기 위한 예시 테이블입니다.

컬럼명	데이터 타입	PK/FK	설명
diary_id	BIGINT	PK	일기 고유 ID
author_id	BIGINT	FK	작성자 ID
content	TEXT		일기 내용
visibility_type_id	INT	FK	이 타입으로 설정된 친구에게만 공개 (NULL 허용 가능)
created_at	DATETIME		작성 일시
4. 주요 로직 구현을 위한 쿼리 예시
시나리오 1: A가 쓴 '찐친 공개' 일기를 B가 볼 수 있는가?
상황:

A(ID: 100)가 B(ID: 200)를 '찐친(Type ID: 2)'으로 설정.

B가 A를 '친구(Type ID: 3)'로 설정.

A가 visibility_type_id = 2 (찐친)인 일기를 작성.

판단 로직: 작성자(A)가 시청자(B)를 어떻게 생각하는지 확인해야 합니다.

쿼리:

SQL
SELECT *
FROM friendships
WHERE user_id = 100       -- 작성자 A
  AND friend_id = 200     -- 시청자 B
  AND assigned_type_id = 2; -- A가 설정한 공개 범위 (찐친)
결과: 위 시나리오대로 데이터가 들어가 있다면 결과가 존재하므로 B는 볼 수 있습니다.

시나리오 2: B가 쓴 '찐친 공개' 일기를 A가 볼 수 있는가?
상황: 위와 동일.

B가 visibility_type_id = 2 (찐친)인 일기를 작성.

판단 로직: 작성자(B)가 시청자(A)를 어떻게 생각하는지 확인해야 합니다.

쿼리:

SQL
SELECT *
FROM friendships
WHERE user_id = 200       -- 작성자 B
  AND friend_id = 100     -- 시청자 A
  AND assigned_type_id = 2; -- B가 설정한 공개 범위 (찐친)
결과: B는 A를 '친구(Type ID: 3)'로 설정했으므로, assigned_type_id = 2 조건에 맞는 데이터가 없습니다. A는 볼 수 없습니다.

시나리오 3: A의 친구 목록과 A가 생각하는 관계 타입 조회
SQL
SELECT
    u.nickname AS 친구닉네임,
    rt.type_name AS 내가_설정한_관계
FROM friendships f
JOIN users u ON f.friend_id = u.user_id
JOIN relationship_types rt ON f.assigned_type_id = rt.type_id
WHERE f.user_id = 100; -- A의 ID
5. 추가 확인이 필요한 질문
설계 과정에서 한 가지 중요한 결정 포인트가 있었습니다. 이 부분에 대해 기획 의도를 확인해주시면 더 완벽한 시스템이 될 것입니다.

질문: 관계 타입 간에 계층 구조(Hierarchy)가 있나요?

현재 설계 (Exact Match): "찐친만 볼 수 있게 설정"하면 정말 '찐친'으로 설정된 사람만 볼 수 있습니다. '가족'으로 설정된 사람은 볼 수 없습니다. (제시해주신 예시를 글자 그대로 해석)

계층 구조 가능성: 보통은 '가족'이 '찐친'보다 더 가깝거나 상위 개념일 수 있습니다. 만약 "찐친 공개" 글을 '가족'도 볼 수 있어야 한다면, 쿼리 조건이 = 이 아니라 관계 타입의 우선순위(priority)를 이용한 >= 혹은 <= 조건으로 변경되어야 합니다.

현재 설계는 제시해주신 예시를 충실히 따르는 Exact Match 방식으로 구현되었습니다. 만약 계층 구조가 필요하다면 말씀해주세요!

가족, 찐친, 친구로 되어 있지만 상하관계는 아니야. 공개여부는 개별로 각각 선택할 수 있어. 그리고 비공개도 있고, 모두선택도 있을거야.

명확한 피드백 감사합니다! 덕분에 요구사항이 훨씬 구체여졌습니다.

변경된 핵심 요구사항 요약:

관계의 평등성 (No Hierarchy): '가족', '찐친', '친구'는 단순한 구분(Label)일 뿐, 그 사이에 상하 관계나 포함 관계는 없습니다. (예: '가족'에게 공개했다고 해서 '찐친'이 자동으로 보는 것은 아님)

다중 선택 공개 (Multiple Selection Visibility): 글을 쓸 때 공개 대상을 하나만 고르는 게 아니라, 여러 개를 선택할 수 있습니다. (예: '가족'과 '찐친'에게만 공개 선택 가능)

비공개 및 전체 공개 지원: 아무것도 선택하지 않으면 '비공개(나만 보기)', 관계 타입 전체를 선택하면 '모두(내 친구들) 공개'가 됩니다.

이 요구사항을 반영하여 DB 설계를 수정했습니다. 가장 큰 변화는 일기 테이블에서 공개 설정 컬럼이 빠지고, 별도의 '공개 권한 매핑 테이블'이 추가되었다는 점입니다.

수정된 친구 관계 시스템 DB 설계 (V2)

2. 테이블 상세 정의 (변경된 부분 중심)
users, friend_requests, friendships 테이블은 이전 설계와 동일합니다. (A와 B의 관계를 두 줄로 나누어 저장하는 핵심 로직 유지)

2.1. relationship_types (수정됨)
상하관계가 없으므로 우선순위(priority) 컬럼을 삭제했습니다.

type_name	VARCHAR(20)		'가족', '찐친', '친구'

2.2. diaries (수정됨)

2.3. diary_visibility (신규 추가 🌟)
"공개 여부 개별 다중 선택"을 구현하기 위한 핵심 테이블입니다. 특정 일기가 어떤 관계 타입들에게 공개되었는지를 매핑합니다.

컬럼명	데이터 타입	PK/FK	설명
diary_id	BIGINT	PK, FK	어떤 일기에 대한 설정인지

동작 방식 예시 (일기 ID 100번을 A가 작성):

비공개 (나만 보기): 이 테이블에 diary_id = 100인 데이터가 아예 없습니다.

'찐친'에게만 공개: (100, 2) 한 줄이 삽입됩니다. (2는 찐친 ID 가정)

'가족'과 '찐친'에게 공개 (개별 선택): (100, 1), (100, 2) 두 줄이 삽입됩니다.

모두 선택: (100, 1), (100, 2), (100, 3) 세 줄이 모두 삽입됩니다.

3. 핵심 로직 쿼리 (검증)
시나리오:

작성자 A (ID: 100)가 일기 (ID: 555)를 작성했습니다.

A는 이 일기의 공개 범위를 '가족(ID:1)'과 '찐친(ID:2)'으로 선택했습니다.

-> diary_visibility 테이블에 (555, 1), (555, 2)가 들어갑니다.

시청자 B (ID: 200)가 이 일기를 보려고 합니다.

A는 B를 **'찐친(ID:2)'**으로 관계를 정의해 둔 상태입니다.

-> friendships 테이블에 (user_id:100, friend_id:200, assigned_type_id:2)가 있습니다.

질문: B는 A의 일기 555번을 볼 수 있는가?

판단 로직:

작성자(A)가 시청자(B)를 어떤 관계 타입으로 설정했는지 찾습니다. -> 결과: '찐친(2)'

그 관계 타입('찐친(2)')이 해당 일기(555)의 공개 허용 목록(diary_visibility)에 포함되어 있는지 확인합니다.

쿼리 (방법 1: EXISTS 활용 - 성능상 유리):

SQL
SELECT d.*
FROM diaries d
WHERE d.diary_id = 555  -- 보고자 하는 일기
  AND d.author_id = 100 -- 작성자 A
  AND EXISTS (
      -- 이 서브쿼리가 참이어야 볼 수 있음
      SELECT 1
      FROM friendships f
      JOIN diary_visibility dv ON f.assigned_type_id = dv.type_id
      WHERE f.user_id = d.author_id   -- 작성자(A)가 정의한 관계에서
        AND f.friend_id = 200         -- 시청자(B)를 찾고
        AND dv.diary_id = d.diary_id  -- 그 관계 타입이 이 일기의 공개 설정에 있는지 확인
  );
-- 결과: 조건이 만족되므로 일기 정보가 조회됨 (볼 수 있음)
쿼리 (방법 2: JOIN 활용 - 이해하기 쉬움): "B의 피드에서 A의 일기를 가져온다"고 가정했을 때의 쿼리입니다.

SQL
SELECT d.diary_id, d.content, d.created_at
FROM diaries d
JOIN users author ON d.author_id = author.user_id
-- 1. 작성자(A)가 시청자(B)를 어떻게 생각하는지 join
JOIN friendships f ON d.author_id = f.user_id AND f.friend_id = 200 
-- 2. 그 관계 타입이 일기 공개 설정에 포함되어 있는지 join
JOIN diary_visibility dv ON d.diary_id = dv.diary_id AND f.assigned_type_id = dv.type_id
WHERE d.author_id = 100;
-- 결과: JOIN이 모두 성공적으로 연결되므로 결과가 나옴 (볼 수 있음)
이 설계는 요청하신 "상하관계 없는 개별 다중 선택" 기능을 완벽하게 지원합니다.

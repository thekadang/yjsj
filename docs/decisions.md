## 📋 ADR 작성 가이드

### 언제 작성하나요?
- 기술 스택 선택 (프레임워크, 데이터베이스, 라이브러리 등)
- 아키텍처 패턴 결정 (MVC, 마이크로서비스, 모놀리식 등)
- 중요한 알고리즘이나 데이터 구조 선택
- 보안, 성능, 확장성에 영향을 주는 결정
- 논란의 여지가 있거나 다른 선택지가 있었던 경우

### 작성 템플릿
```markdown
## ADR-XXX: [결정 제목]

**날짜**: YYYY-MM-DD
**상태**: 제안됨 / 승인됨 / 대체됨 / 폐기됨

### 상황 (Context)
- 어떤 문제를 해결하려고 하는가?
- 현재 상황과 제약사항은?

### 결정 (Decision)
- 무엇을 선택했는가?
- 구체적인 구현 방법은?

### 결과 (Consequences)
- 장점: 이 결정으로 얻는 이점
- 단점: 이 결정의 트레이드오프
- 리스크: 잠재적 위험 요소
```

### ADR-001: Node.js + Express + React 선택
**날짜**: 2025-12-02
**상태**: 승인됨

#### 상황
- 웹 기반의 영정사진 보관 및 유산 관리 서비스 구축
- 빠른 개발 속도와 풍부한 생태계 필요
- 프론트엔드와 백엔드의 언어 통일성 고려

#### 결정
**Node.js (Express) + React (Vite)** 선택

**고려한 대안**:
1. Python (FastAPI/Django) - 데이터 분석에 강점이 있으나 웹 개발 속도 및 인력 풀 고려 시 Node.js가 유리
2. Java (Spring Boot) - 엔터프라이즈급 안정성이 있으나 초기 설정 및 개발 속도가 느림

#### 결과
**장점**:
- JavaScript/TypeScript로 풀스택 개발 가능
- 방대한 npm 생태계 활용
- React의 강력한 컴포넌트 시스템 및 UI 라이브러리 활용

**단점**:
- 싱글 스레드 기반으로 CPU 집약적 작업에 취약할 수 있음 (이미지 처리 등) -> 별도 워커나 서비스로 분리 고려

**리스크**:
- 비동기 처리 복잡성 -> async/await 및 철저한 에러 핸들링으로 완화

### ADR-003: 클라우드 인프라 비교 (AWS vs GCP)
**날짜**: 2025-12-02
**상태**: **GCP 제안됨** (사용자 검토 필요)

#### 상황
- 초기 비용을 최소화하면서도 확장성 있는 인프라 필요
- `수익지출_예상서`는 AWS 기준으로 작성되었으나, 스타트업 환경에서 GCP의 이점(Serverless, DX)을 고려해볼 필요가 있음

#### 비교 분석

| 항목 | AWS (Amazon Web Services) | GCP (Google Cloud Platform) |
|:---:|:---|:---|
| **아키텍처** | **EC2 (VM) + RDS** (전통적 방식) | **Cloud Run (Serverless) + Cloud SQL** (현대적 방식) |
| **프론트엔드** | S3 + CloudFront | **Firebase Hosting** (Google CDN 포함) |
| **장점** | • 12개월 프리티어 (EC2, RDS) 강력함<br>• 가장 널리 쓰이는 표준<br>• 세밀한 인프라 제어 가능 | • **서버 관리 불필요 (Serverless)**<br>• 트래픽 0일 때 비용 0원 (Cloud Run)<br>• Firebase의 압도적인 개발 편의성<br>• React 앱 배포가 매우 간편 |
| **단점** | • 서버 관리(OS 업데이트, 스케일링 설정) 필요<br>• 설정이 복잡함 | • Cloud SQL의 프리티어가 제한적 (비용 발생 가능성)<br>• AWS보다 레퍼런스가 적을 수 있음 |
| **예상 비용 (초기)** | **매우 낮음** (프리티어 활용 시 월 0~1만원 수준) | **낮음** (Cloud Run 무료, Cloud SQL 약 1~2만원) |
| **확장성** | Auto Scaling Group 설정 필요 (복잡) | **자동 스케일링** (기본 기능, 매우 빠름) |

#### 제안: GCP (Google Cloud Platform)

**이유**:
1. **관리 편의성**: 초기 개발 단계에서 서버 관리(OS 패치, 로드밸런서 설정 등)에 시간을 쏟는 것보다 서비스 개발에 집중하는 것이 유리합니다. Cloud Run은 이를 완벽히 해결해줍니다.
2. **Firebase 생태계**: React 앱 배포(Hosting), 인증(Auth), 푸시 알림(FCM) 등을 Firebase 하나로 통합 관리할 수 있어 개발 속도가 획기적으로 빨라집니다.
3. **유연한 비용**: 사용자가 없을 때는 비용이 0원에 수렴하는 Serverless 구조가 초기 스타트업에 적합합니다. (단, DB 비용은 발생)

#### 구체적 구성안 (GCP)
- **Frontend**: Firebase Hosting (글로벌 CDN 자동 적용, SSL 무료)
- **Backend**: Cloud Run (Docker 컨테이너 기반, 자동 스케일링)
- **Database**: Cloud SQL for PostgreSQL (가장 작은 인스턴스 시작) 또는 Supabase(PostgreSQL 기반 PaaS) 활용 고려
- **Storage**: Cloud Storage (이미지 저장)

#### 결과
**장점**:
- **No Ops**: 인프라 관리에 드는 시간 최소화
- **Fast Deploy**: GitHub 연결만으로 자동 배포 파이프라인 구축 용이
- **Scalability**: 트래픽 급증 시 즉각 대응 가능

**리스크**:
- Cloud SQL 비용이 AWS RDS 프리티어보다 초기에 더 나올 수 있음 (월 1-2만원 예상). 하지만 인건비와 관리 시간을 고려하면 이득.

### ADR-004: 디자인 마이그레이션 전략
**날짜**: 2025-12-02
**상태**: 승인됨

#### 상황
- 기존 WordPress(Elementor)로 제작된 디자인을 유지해야 함
- React 기반의 SPA로 전환 필요

#### 결정
**"Componentization (컴포넌트화)"** 전략 채택
- 기존 HTML/CSS를 분석하여 React 컴포넌트로 재구현
- Elementor 생성 클래스명을 의미 있는 이름으로 리팩토링하되, 스타일은 최대한 유지
- `css/` 폴더의 스타일을 React 모듈 CSS 또는 Tailwind CSS로 변환 (Tailwind 권장)

#### 결과
**장점**:
- React의 재사용성 및 상태 관리 이점 활용
- 불필요한 WP 스크립트 제거로 성능 향상
- 유지보수 용이성 확보

**단점**:
- 초기 마이그레이션 공수 발생 (단순 복사/붙여넣기 불가)

### ADR-005: 미디어 처리 및 저장 전략
**날짜**: 2025-12-02
**상태**: 승인됨

#### 상황
- 고화질 영정사진(10MB+)과 음성 일기(1MB)의 효율적 관리 필요
- 트래픽 비용 절감 및 사용자 경험(로딩 속도) 최적화 필수

#### 결정
1. **이미지 이원화 (Two-Track)**:
   - **원본**: S3/GCS에 보관 (인쇄용, 300dpi 이상)
   - **썸네일**: 업로드 시 자동 생성 (웹 표시용, 300KB 내외)
2. **오디오 포맷**:
   - MP3 또는 AAC (128kbps) 사용
   - 클라이언트 측 압축 또는 서버 변환 적용
3. **크롭 툴 제공**:
   - 프론트엔드에서 11:14 비율 크롭 기능 제공

#### 결과
**장점**:
- 트래픽 비용 90% 이상 절감 예상
- 웹사이트 로딩 속도 획기적 개선
- 인쇄 품질 보장
